# 浏览器导航助手 · 需求理解文档（第 2 轮）

> 依据：`PROBLEM.md`、`resource.json`（样例数据）。
> 本轮只做需求理解，不涉及具体设计与编码。
> 第 2 轮：第 11 节的待确认问题已全部定案（D-01 ~ D-18，另有新增决策 D-19 ~ D-27），以 [`02-PRD.md`](02-PRD.md) 第 12 章和 `docs/trace/features.json` 的 decisions 为准；原始需求点见 `docs/trace/requirements.json`。
> 标记说明：**【明确】** 文档原文要求；**【推断】** 文档没写明，但要满足明确要求就必须做到的隐含要求；**【待确认】** 存在歧义、需要你拍板（附我的建议默认值）。

## 1. 一句话理解

做一个 **Chrome MV3 插件 + 本地后端**：插件采集「当前页 / 当前窗口打开的 tabs / 最近浏览历史」，过滤隐私 URL 后同步到后端。后端在内存里维护按 URL 去重的页面库，基于「访问模式（最近访问、频次、是否打开、域名）+ 用户的自然语言规则」给出 **历史排序、下一步推荐、旧页面和重复页面的整理建议**，再通过 **健康检查 + 配置查询 + 插件诊断面板** 保证整套系统能在本地跑通，出了问题能快速定位。

核心考察点（按文档的侧重理解）：

1. MV3 插件结构、权限配置、popup ↔ background 通信是否清楚；
2. 评分、推荐、整理规则是否**可解释**（不追求算法复杂度）；
3. 自然语言 → 结构化规则 → 规则真正作用到排序和整理上，整个闭环能演示出来；
4. **启动诊断与排障能力**（文档原文称其为"重要考察点"）；
5. 能回答性能、降级、边界情况、隐私相关的追问。

## 2. 硬性约束清单

| # | 约束 | 来源 | 对实现的影响 |
|---|---|---|---|
| C1 | 插件必须基于 Chrome Extension Manifest V3 | 总体约束 | `manifest_version: 3`；后台使用 Service Worker（浏览器随时可能回收它，不能用全局变量保存状态）；popup 禁止内联脚本（MV3 CSP），不能加载远程代码 |
| C2 | 权限至少包含 `tabs`、`history`、`storage`、`activeTab` | 必做 1 | manifest 必须声明；【推断】访问本地后端还需要 `host_permissions`（如 `http://localhost/*`），做右键菜单还需要 `contextMenus` |
| C3 | 后端语言和框架不限 | 总体约束 | 自选 |
| C4 | 可以用内存存储，但要能解释真实的持久化方案 | 总体约束 | 内存实现即可交付；文档中给出持久化方案（表结构、索引） |
| C5 | 不要求真实调用 LLM，推荐和规则解析可以 mock 或用规则引擎实现 | 总体约束 | 规则解析用关键词 / 正则实现，不引入任何外部模型 API |
| C6 | 不允许直接用完整成熟的推荐系统平台作为核心实现 | 总体约束 | 评分、推荐、去重逻辑必须自己写 |
| C7 | 隐私敏感 URL（含 password、token、bank 等关键词）**不应上传到后端** | 总体约束 | 过滤必须发生在**插件侧、发送之前**；后端二次过滤只能兜底，不能替代插件侧过滤 |
| C8 | 所有功能都要能在本地完整演示 | 总体约束 | 运行时不依赖任何云服务或外网 API |
| C9 | 可以用 AI 辅助，但要能解释插件结构、权限配置、通信逻辑和数据模型 | 总体约束 | 代码保持简单直白，并配套文档 |
| C10 | popup 与 background 不共享内存，需要通过消息通信；由 background 调用 tabs/history API、与后端通信、管理同步状态和本地缓存 | 架构说明 + 提示 | popup 只负责展示和交互，所有浏览器 API 调用和后端请求都经过 background |
| C11 | 接口路径和 JSON 字段使用文档给定的格式 | 必做 2–7 | 字段名用 camelCase，与示例保持一致；可以增加字段，不能改名或删字段 |

## 3. 系统边界与模块职责

```
┌──────────────── Chrome 插件 (MV3) ────────────────┐         ┌──────── 后端服务 ─────────┐
│                                                    │         │                            │
│  Popup  ──runtime.sendMessage──►  Background       │──fetch─►│  /api/sync                 │
│ (展示/交互) ◄────── 响应 ──────  Service Worker      │         │  /api/pages/ranked         │
│                                      │             │         │  /api/recommendations/next │
│                 chrome.tabs / chrome.history       │         │  /api/pages/cleanup-...    │
│                 chrome.storage.local               │         │  /api/rules(/parse)        │
│                 （缓存、同步状态、API 地址）           │         │  /api/health  /api/config  │
│                                                    │         │  内存存储（可替换为持久化）   │
│  （可选）Content Script：网页内高亮                  │         │                            │
└────────────────────────────────────────────────────┘         └────────────────────────────┘
```

| 模块 | 职责【明确】 | 补充理解【推断】 |
|---|---|---|
| Popup | 展示当前页标题和 URL、同步按钮和同步状态、推荐、历史排序概览、整理建议摘要、自然语言配置输入框、诊断状态入口；另外要展示当前窗口的 tabs 列表、最近 N 条历史（必做 1） | 信息量大，需要分区或分 Tab 展示；popup 一失焦就会关闭，所以耗时操作必须放在 background，popup 重新打开时从 storage 读取状态 |
| Background SW | 响应 popup 操作；调用 tabs/history API；与后端通信；管理同步状态和本地缓存 | 隐私过滤在这里做；SW 随时可能被回收，状态写入 `chrome.storage.local` |
| Content Script | 可选（如高亮推荐关键词） | 在 `chrome://` 等系统页面无法注入，需要降级 |
| 后端 | 接收并存储行为数据；评分排序；推荐下一步；识别旧页面和重复页面；解析自然语言规则；健康检查和配置查询 | 规则保存后要立即影响排序和整理结果 |

## 4. 数据模型理解

### 4.1 Page

| 字段 | 理解 |
|---|---|
| `id` | 后端生成 |
| `url` | 原始 URL，**作为存储去重的主键**【推断】 |
| `normalizedUrl` | 去掉 query / hash 后的 URL，用来**识别疑似重复**（merge），不用于存储去重【推断】。理由：样例中的 `issues/123` 和 `issues/123?tab=comments` 必须作为两条记录存在，整理接口才能给出 merge 建议；如果存储时就按 normalizedUrl 合并，merge 建议永远不会出现 |
| `domain` | 取 hostname |
| `visitCount` | 访问次数。语义有歧义，见 Q2 |
| `lastVisitedAt` / `firstSeenAt` | 毫秒时间戳；`firstSeenAt` 理解为后端第一次见到该页面的时间 |
| `sources` | **数组**，取 `active_tab` / `open_tab` / `history` 的并集，多次同步会累积 |
| `isOpen` | 当前是否打开。【推断】必须按「最近一次同步的快照」刷新：本次同步里不在 activeTab / openTabs 中的页面要置为 false，否则「不在当前打开的 tab 中才归档」的判断会出错 |
| `isArchived` | 模型里有这个字段，但文档没有定义「执行归档」的接口，所以默认 false；是否实现归档动作见 Q15 |
| `score` | 计算得出，取值 0–1 |

注意：`/api/pages/ranked` 返回的每一项比 Page 多一个 `reason`、少若干字段。也就是说，返回的是 Page 的一个视图（DTO），不是把 Page 原样输出。

### 4.2 Rule

| 字段 | 理解 |
|---|---|
| `type` | 文档明确定义了两种：`archive_candidate`（对应 `action: suggest_archive`，使用 `domain` / `urlPattern` / `inactiveDays`）和 `never_archive`（对应 `action: keep`，使用 `domain`） |
| `domain` / `urlPattern` / `inactiveDays` | 按类型可选；`never_archive` 的示例里没有 `urlPattern` 和 `inactiveDays` |
| `rawText` | 示例中都写的是 `"..."`，存整句还是拆分后的子句没有说明，见 Q9 |
| `enabled` | Rule 模型里有，parse 返回的示例里没有，保存时默认 `true` |
| `id` | parse 返回里已经带了 `rule_1`，但 parse 阶段规则还没有保存，见 Q8 |

背景部分还提到两类自然语言诉求，但文档**没有给它们定义 type**：

- "如果我连续看了 3 个 React 文档，推荐相关 MDN 页面"（推荐类规则）
- "不要上传包含 password、token 的 URL"（隐私类规则）

我的理解：必做范围是 `archive_candidate` + `never_archive`，另外两类属于可扩展项，见 Q10。

### 4.3 Recommendation

字段：`id`、`type`（固定为 `next_visit`）、`url`、`title`、`score`、`reason`、`createdAt`。接口返回示例里省略了 `id` / `createdAt`，返回时带上即可（字段只增不减）。

## 5. 必做功能拆解

### F1 插件加载并读取浏览器上下文

- 【明确】提供合法的 `manifest.json`，至少声明 `tabs`、`history`、`storage`、`activeTab`；能在开发者模式下加载。
- 【明确】popup 展示：active tab 的 URL 和 title；**当前窗口**打开的 tabs（URL、title）；最近 N 条历史（N=50 或 100）。
- 【推断】N 取 100，与 `/api/config` 里的 `maxHistoryItems=100` 保持一致。
- 【推断】F1 只依赖浏览器 API、不依赖后端，后端挂了也要能正常展示。这本身就是一种降级。
- 注意点：
  - `chrome.history.search` 默认只查最近 24 小时，要显式传 `startTime` 才能拿到更早的历史；
  - active tab 可能是 `chrome://`、新标签页等系统页面，需要能正常展示，并标记为「不可同步」。

### F2 浏览器数据同步到后端

- 【明确】popup 按钮 →（background）→ 把 activeTab / openTabs / history 发给 `POST /api/sync`，请求体格式固定。
- 【明确】后端按 URL 去重保存；更新 `visitCount` / `lastVisitedAt`；区分 source；插件展示同步成功状态。
- 【推断】发送前在插件侧做隐私过滤（C7）；非 http(s) 的 URL（`chrome://`、`chrome-extension://`、`about:`、`file://`）不上传。
- 【推断】history 项除了 `url/title/lastVisitTime`，还可以带 `visitCount`（样例数据和 Chrome 的 `HistoryItem` 都有这个字段）。
- 【推断】同步结果（时间、成功或失败、条数、错误信息）持久化到 `chrome.storage.local`，供诊断项「最近一次同步」使用。
- 【待确认】文档没给 `/api/sync` 的返回格式，见 Q16。
- 样例细节：`resource.json` 中的 activeTab **不在** openTabs 里，而真实调用 `chrome.tabs.query({currentWindow: true})` 会把 active tab 也一起返回。后端要能正确合并这两种情况。

### F3 历史排序接口 `GET /api/pages/ranked`

- 【明确】返回 `pages[]`，每项包含 `url, title, domain, visitCount, lastVisitedAt, score, reason`，按 score 降序排列。
- 【明确】评分要可解释，参考公式 `recency*0.4 + frequency*0.3 + isOpenBoost*0.2 + domainBoost*0.1`；不要求复杂算法，但要能讲清楚各个维度和取舍。
- 【明确】「整理建议和**排序接口**需要读取规则执行」，即规则必须影响排序。但文档**没说怎么影响**，见 Q5。
- 【推断】`reason` 根据贡献最大的几个维度生成中文说明，例如「最近 3 天多次访问，且当前仍处于打开状态」。
- 文档没有给出 `domainBoost` 的定义，也放在 Q5 里一起确认。

### F4 推荐下一步访问 `POST /api/recommendations/next`

- 【明确】入参为 `currentPage`、`openTabs`、`recentHistory`；出参为 `recommendations[]`（type / url / title / score / reason）。
- 【明确】最小规则集：
  1. 当前页是 GitHub PR → 推荐同 repo 的 issue / actions；
  2. 当前页是文档页 → 推荐同域名的高频页面；
  3. 当前页的域名与某些历史页面相同 → 推荐同域名的高分页面；
  4. 排除当前已打开的页面和重复 URL。
- 【推断】排除当前页本身；「重复 URL」按 normalizedUrl 判断（例如 `issues/123?tab=comments` 和已打开的 `issues/123` 视为重复）。
- 【推断】验收要求「至少 1 条，有 reason」。所以上面的规则都没命中时需要兜底策略（例如取全局高分且未打开的页面），保证不会返回空列表。
- 【推断】「文档页」需要一个判定口径（如 `developer.mozilla.org`、`react.dev`，或路径包含 `/docs/`、`/reference/`、`/learn`），见 Q17。
- 【明确】（提示部分）推荐接口要快，不要每次都全量扫描历史。

### F5 旧页面与重复页面整理建议 `GET /api/pages/cleanup-suggestions`

- 【明确】返回 `suggestions[]`，共三种 action：
  - `archive`：`url, title, reason`
  - `merge`：`urls[], reason`
  - `keep`：`url, reason`
- 【明确】基础规则：超过 X 天未访问、且不是当前打开的 tab → archive；去掉 query/hash 后 URL 相同 → merge；被 `never_archive` 保护的域名不归档。
- 【推断】X 默认取 `cleanupThresholdDays = 14`（示例 reason「超过 14 天未访问」与 config 一致）；`archive_candidate` 规则按 `domain + urlPattern + inactiveDays` 覆盖默认阈值（例如 GitHub issue 用 7 天）。
- 【推断】判定优先级：当前打开 > `never_archive` 保护 > `archive_candidate` 规则 > 全局阈值。reason 中注明命中了哪条规则，方便验收第 9 步证明「建议与规则配置一致」。
- 【待确认】`keep` 的展示范围见 Q6；判断「多少天没访问」用什么时间基准见 Q1；搜索页去掉 query 后被误判为重复的问题见 Q7。

### F6 自然语言规则配置

- 【明确】流程：popup 输入框 → `POST /api/rules/parse` → **展示解析结果** → 用户确认 → `POST /api/rules` 保存。
- 【明确】可以查看规则列表、可以删除规则；整理建议和排序接口要读取规则。
- 【推断】文档没给列表和删除接口的路径，按 REST 惯例定为 `GET /api/rules`、`DELETE /api/rules/:id`。
- 【明确】解析器至少要识别 **N 天没访问、域名、动作词**；示例中的一句话要拆成 2 条规则（按「，但」等连接词拆分）。
- 【推断】解析器需要处理的要点：
  - 产品名映射到域名（"GitHub" → `github.com`），对象词映射到 urlPattern（"issue" → `/issues/`）；也要识别直接写出的域名（如 `docs.internal.com`）；
  - **先判断否定**：「永远不要归档」里包含「归档」二字，必须先识别否定，否则会被解析成相反的意思；
  - 识别不了的内容要明确告诉用户（这也是文档列出的追问点）：返回中增加 `warnings` / 未识别片段，不保存无效规则。

### F7 启动诊断与配置检查（重点考察项）

插件端的 7 个检查项，以及我理解的检查方式：

| 检查项 | 文档说明 | 检查方式【推断】 | 失败时的提示 |
|---|---|---|---|
| 后端是否可连接 | 调用 `/api/health` | 带超时请求 health，展示 version / uptime | 后端未启动 / 地址填错 / 被 CORS 或 host_permissions 拦截 |
| `tabs` 权限 | 检查 manifest 权限配置 | `chrome.permissions.contains`，再实际调用 `chrome.tabs.query` 探测 | manifest 缺少权限，改配置后需要重新加载插件 |
| `history` 权限 | 同上 | `chrome.permissions.contains`，再实际调用 `chrome.history.search` 探测 | 同上 |
| `storage` 可用 | 检查本地存储可用性 | 写入 → 读取 → 删除一个探测 key | — |
| API base URL | 展示当前配置的后端地址 | 从 storage 读取，未配置时用默认值；校验格式 | 地址填写错误（是否允许修改见 Q11） |
| 最近一次同步 | 展示最近同步时间和结果 | 读取 storage 中的同步记录 | 展示失败原因 |
| 当前规则数量 | 已保存的规则条数 | 取 health 返回的 `ruleCount` | — |

后端：

- `GET /api/health` → `{status, version, uptime(秒), pageCount, ruleCount}`
- `GET /api/config` → `{cleanupThresholdDays, maxHistoryItems, enablePrivacyFilter, privacySensitiveKeywords}`
- 【推断】插件从 `/api/config` 拉取隐私关键词和 `maxHistoryItems`；后端不可用时使用插件内置的默认值。
- 【明确】交付物要求「诊断说明（诊断项含义和排查方法）」，所以每个检查项失败时都要给出排查建议，不能只亮红灯或绿灯。

## 7. 进阶项（加分项，可做可不做）

| 进阶项 | 与必做项 / 追问的关系 | 建议优先级 |
|---|---|---|
| 隐私过滤（插件侧过滤 + 关键词可配置） | 基础过滤已经被 C7 列为总体约束，实际上是必做；「关键词可配置」才是加分部分 | P0（基础过滤）/ P1（可配置） |
| 本地持久化（缓存推荐和排序结果，离线可查看） | 直接回答「后端不可用怎么降级」 | P1 |
| 增量同步（记录同步游标） | 回答性能追问，改动量小 | P1 |
| 快速响应优化（推荐缓存、预计算评分） | 直接回答「10 万条如何 100ms 返回」 | P1 |
| 后端持久化（SQLite / 文件） | 回答持久化追问；C4 只要求能解释清楚 | P2 |
| 右键菜单（添加到分析 / 标记为重要） | 「标记为重要」可以作为 domainBoost 的信号来源 | P2 |

## 12. 面试追问预判（先记要点，设计阶段再展开）

- **历史记录有 10 万条时，推荐接口如何保持 100ms 内返回**：同步时预计算 score；按 domain / repo 建索引，只取候选子集；每个桶只保留 Top-K；推荐结果按「当前 URL + 数据版本」缓存；增量同步减少写入量；持久化时给 `domain`、`lastVisitedAt`、`normalizedUrl` 建索引。
- **后端不可用时插件如何降级**：F1 照常工作（只依赖浏览器 API）；展示本地缓存的排序和推荐结果，并标注「离线 · 缓存于 xx」；记录同步失败的原因，诊断面板给出排查建议。
- **规则解析能处理哪些边界情况**：多子句拆分、否定词、中文数字（「七天」）、「周 / 月」等时间单位、未知的产品名、规则冲突（保护优先）。无法识别时返回未识别片段并提示用户，不保存。
- **隐身模式下 history API 有什么变化**：隐身浏览不会写入历史，history API 拿不到这部分记录；插件默认不在隐身窗口运行，用户手动允许后才能看到隐身 tab（`tab.incognito = true`），这类 tab 应该跳过、不上传。

## 13. 风险点

1. SW 生命周期：全局变量会丢失，状态一律放在 `chrome.storage` 中。
2. `chrome.history.search` 默认只查最近 24 小时，必须显式传 `startTime`。
3. popup 失焦就会关闭：同步在 background 中完成，popup 重新打开后从 storage 读取状态。
4. MV3 CSP 禁止内联脚本：popup 的 JS 必须放在独立文件里。
5. 插件访问 localhost 的跨域问题：同时配置 `host_permissions` 和后端 CORS。
6. 时间基准（Q1）和演示数据（Q12）直接影响验收第 6、9 步的效果。
7. active tab 是 `chrome://` 等系统页面时，同步、推荐和 content script 都要做降级处理。
