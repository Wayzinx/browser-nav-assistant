# 浏览器导航助手 · 技术方案（插件前端）

> 负责人：前端架构师（插件 / 前端会话 agent）。输入：`PROBLEM.md`、`docs/02-PRD.md`、`docs/trace/features.json`、`specs/frontend.spec.md`、`docs/prototype/`。

## 0 摘要

- MV3 + 原生 JS（ES modules），**无构建步骤、无 npm 依赖**，`extension/` 可直接「加载已解压的扩展程序」。
- **popup 只做展示与交互**；`chrome.tabs` / `chrome.history`、后端通信、隐私过滤、同步状态、缓存、诊断全部在 background（Service Worker）中完成，popup ↔ background 走统一信封的消息协议（§4）。
- 所有需要保留的状态写 `chrome.storage.local`（§6），SW 内存只作可丢失缓存。
- 为了按模块并行开发，采用 **「注册表 + 每模块一个文件」**：background 的 `handlers/index.js`、popup 的 `views/index.js` 由 lead（CORE）预先注册全部模块文件，模块开发者只改自己的文件（§11 文件所有权表）。
- 可测试性：storage key `apiBaseUrl`、popup 路径 `popup/popup.html` 与测试夹具一致；所有可交互 / 需断言元素都有 `data-testid` 并登记在 ui-contract；以 tab 方式打开 popup 时「当前页面」排除插件自身页面（§5.1 算法）；历史读取显式传 `startTime`；后端不可用时展示缓存并标注离线。

与 `specs/frontend.spec.md` 推荐目录（FE-DIR-02）的差异与理由：

| 差异 | 理由 |
|---|---|
| `handlers/` 按**模块**一个文件（而非每个 type 一个文件） | 并行开发按模块分工，每个模块恰好拥有一个 handler 文件，注册表只需 lead 写一次 |
| `services/` 中 sync 拆为 `sync.js` / `sync-state.js` / `sync-payload.js`，诊断拆为 `diag-checks-env.js` / `diag-checks-backend.js` / `diag-report.js` | 控制单文件 ≤ 300 行（FE-STYLE-04），并让每个 Code ID 落在可独立测试的函数上 |
| 新增 `background/services/storage.js`、`current-page.js`、`cursor.js`、`privacy-config.js`、`recovery.js`、`context-menu.js` | 分别对应 CORE / CTX / INCR / PRIV / CACHE / MENU 模块的独立文件，避免同文件跨模块（validator CONFLICT） |

| 每个视图一个 `popup/views/<view>.css`（而非单个 popup.css） | 样式按模块归属，模块开发不改 CORE 的 popup.css；popup.css 只放设计令牌、布局与通用组件（§11.2 ④） |

## 2 manifest 权限及理由

```json
{
  "manifest_version": 3,
  "name": "浏览器导航助手",
  "version": "1.0.0",
  "permissions": ["tabs", "history", "storage", "activeTab", "contextMenus"],
  "host_permissions": ["http://localhost/*", "http://127.0.0.1/*"],
  "background": { "service_worker": "background/service-worker.js", "type": "module" },
  "action": { "default_popup": "popup/popup.html", "default_title": "导航助手" }
}
```

| 权限 | 用途 | 不申请会怎样 |
|---|---|---|
| `tabs` | 读取所有标签页的 `url` / `title` / `lastAccessed` / `incognito`，用于当前页判定、上下文列表、同步；`tabs.create` 打开推荐页 | 只能拿到 activeTab 的 URL，无法展示 / 上传 openTabs |
| `history` | `chrome.history.search` 读取最近 30 天、最多 100 条历史 | 无法上传历史，排序和整理失去数据 |
| `storage` | `chrome.storage.local` 保存 apiBaseUrl、同步状态、游标、缓存、忽略记录等 | SW 被回收后状态全部丢失 |
| `activeTab` | PROBLEM.md 要求的最小权限之一；用户点击右键菜单 / 工具栏图标时临时访问当前页 | 题目验收项不满足 |
| `contextMenus` | 「添加到分析」「标记为重要」右键菜单（F-MENU-01，D-15 纳入 P1） | 右键菜单不可用 |
| `host_permissions` `http://localhost/*`、`http://127.0.0.1/*` | 访问本机后端（匹配模式不写端口即匹配任意端口，覆盖 3000 / 4100 等测试端口） | fetch 被 CORS 拦截 |

- 不申请 `<all_urls>`、`scripting`、`alarms`（不做定时任务；同步由用户或恢复检测触发）。其他主机的后端地址通过诊断页修改，未授权时给出 warning（D-11 中的 `optional_host_permissions` 动态申请留作后续）。
- 不声明 `icons` / `action.default_icon`：MV3 不要求图标，不声明可避免图标文件缺失时「Could not load icon」导致加载失败（F-CTX-02）；工具栏使用 Chrome 默认图标。
- 不声明 `content_security_policy`，沿用 MV3 默认（禁止内联脚本和远程代码，FE-MV3-04）。popup.html 只通过 `<script type="module" src="popup.js">` 加载脚本。

## 4 消息协议（popup ↔ background）

信封（FE-MSG-02）：请求 `{ type, payload, requestId }`，响应 `{ ok: true, data }` 或 `{ ok: false, error: { code, message } }`。

- popup 侧 `send()`（C-FE-CORE-07）统一生成 `requestId = pop_<ts>_<seq>`，默认 10 秒超时（SYNC_NOW 15 秒，大于后端 8 秒超时 + 采集时间），超时返回 `{ ok:false, error:{ code:'TIMEOUT' } }`，视图显示错误状态而不是一直转圈（FE-MSG-04）。
- background 路由（C-FE-CORE-02）：`handlers[type]` 不存在返回 `UNKNOWN_MESSAGE`；处理函数抛出的异常转成 `{ ok:false, error:{ code: e.code || 'INTERNAL', message } }`。
- 处理函数调用 api-client 拿到 `{ ok:false, error }` 时，直接构造带 code 的错误抛出，由路由统一包装。

| type | 模块 | 请求 payload | 响应 data（摘要） |
|---|---|---|---|
| `GET_CONTEXT` | CTX | `{}` | `currentPage`、`tabs[]`（含 badge）、`history[]`、`historyQuery{startTime,maxResults}`、`privacy{enabled,keywords,source}` |
| `SYNC_NOW` | SYNC | `{ mode:'auto'\|'full', trigger }` | `syncState`、`result`、`alreadyRunning`（本 SW 已有同步在进行，复用同一次结果，未发第二次 POST）、`fullReason` |
| `GET_SYNC_STATE` | SYNC | `{}` | `syncState`（读取时做 30 秒中断检测，仅当本 SW 无进行中的同步） |
| `GET_RANKED` | RANK | `{ limit, openOnly, domain, source }` | `pages`、`total`、`domains`（取后端 domains）、`fromCache`、`offline`、`cachedAt`；只有无筛选 + 默认 limit 的请求读写 `cache.ranked`，带筛选的离线时返回 `NO_CACHE`「筛选需要在线」（§5.6） |
| `GET_RECOMMENDATIONS` | REC | `{ source }` | `recommendations`、`contextUrl`（实际发送的 currentPage.url，被过滤为 null）、`fromCache`、`offline`、`cachedAt` |

| `PARSE_RULE` | RULE | `{ text }` | `rules`、`unparsed[{ text, reason, examples: string[] }]`、`warnings: string[]`（原样透传） |
| `SAVE_RULES` | RULE | `{ rules }` | `rules`（正式 id）、`ruleCount` |
| `LIST_RULES` | RULE | `{ source }` | `rules`、缓存标记 |

## 5 background 流程

### 5.1 当前页面判定（FE-CTX-01，D-25，C-FE-CTX-01）

popup 以 action 弹窗打开时，活动标签页就是用户正在看的页面；测试夹具以 **tab 方式**打开 `chrome-extension://<id>/popup/popup.html`，此时活动标签页是插件自身页面，必须排除。算法：

```
resolveCurrentPage():
  own = 'chrome-extension://' + chrome.runtime.id + '/'
  [active] = tabs.query({ active: true, lastFocusedWindow: true })
  if active && !active.url.startsWith(own) && !active.incognito:
      return toPage(active)                       // http(s) → 普通页；其他协议 → isSystem=true
  candidates = tabs.query({ lastFocusedWindow: true })
               .filter(t => !t.url.startsWith(own) && !t.incognito)
  web = candidates.filter(t => isHttpUrl(t.url))
  if web.length: return toPage(maxBy(web, t => [t.lastAccessed ?? 0, t.id]))
  if candidates.length: return { ...toPage(maxBy(candidates, …)), isSystem: true }
  return { url: null, title: '', isSystem: true }
toPage(t) = { tabId: t.id, url: t.url, title: t.title || t.url, isSystem: !isHttpUrl(t.url) }
```

- `lastAccessed`（Chrome 121+）缺失时退化为 `tab.id` 较大者（后创建）。
- 依次打开 PR #456、MDN Fetch、popup 标签页时，候选中 MDN 的 `lastAccessed` 最大 → 当前页为 MDN（F-CTX-04 AC1）；只有插件页和 `about:blank` / `chrome://` 时 → 系统页（AC2）。
- 推荐请求中的 `currentPage` 使用同一算法；凡系统页、无痕页、敏感词命中或 `url` 为空，一律**显式传 `currentPage: null`**（保留该 key，缺失会被后端 400 VALIDATION_FAILED），后端退化为全局高分；否则只传 `{ url, title }`，不带 `isSystem` / `tabId` / `badge` 等内部字段。
- 推荐请求的 `openTabs` 与同步口径一致，用 `listAllNormalTabs()`（所有普通窗口，去掉无痕与本插件页，最多 200 条，低于契约 500 上限），保证后端「排除已打开页」覆盖其他窗口；上下文页签的**展示**仍只用当前窗口。

### 5.2 采集（C-FE-CTX-02、C-FE-CTX-03）

- 上下文页签：`tabs.query({ lastFocusedWindow: true })`，去掉本插件页和 `incognito` 标签页（F-PRIV-04），系统页保留并标注「系统页 · 跳过」。
- 同步：`tabs.query({ windowType: 'normal' })`（所有普通窗口，D-21），去掉 incognito，最多 200 个。

### 5.3 同步（C-FE-SYNC-02 ~ 05）

```
SYNC_NOW(payload)                            // handlers/sync.js（C-FE-SYNC-02）
 ├─ joined = isSyncInFlight()
 ├─ r = await runSync({ mode, trigger })     // 单飞：已有同步时拿到同一个 Promise
 └─ return r.ok ? { ...r.data, alreadyRunning: joined } : throw r.error

let inFlight = null                          // services/sync.js（C-FE-SYNC-03）模块级
runSync(opts):
 ├─ if inFlight → return inFlight            // 快速双击 / 点击与自动恢复同时发生：只发 1 次 POST
 ├─ inFlight = doSync(opts).finally(() => inFlight = null)   // 在第一个 await 之前同步赋值
 └─ return inFlight
doSync({ mode, trigger }):
 ├─ state = loadSyncState()
 ├─ markSyncing({ startedAt: now, trigger })  → storage.syncState（popup 收到 onChanged，按钮置灰）
 ├─ privacy = getPrivacyConfig()            // §5.5 → { enabled, keywords, source }
 ├─ health = callApi('GET','/api/health')          // 3 s；失败不阻断
 ├─ win = resolveHistoryWindow({ syncState: state, mode, now, lookbackDays, maxResults, health, apiBaseUrl })
 │                                          // §5.4 → { mode, startTime, maxResults, cursor?, fullReason? }
 ├─ snapshot = { active: resolveCurrentPage(), tabs: listAllNormalTabs(), history: readHistory(win) }
 ├─ { payload, filteredCount, skippedSystem } = filterForUpload(snapshot, privacy)
 ├─ body = buildSyncPayload(payload, win)   // activeTab / openTabs / history / mode / cursor / clientVersion
 ├─ r = callApi('POST', '/api/sync', body, { timeoutMs: 8000 })        // 不重试
 ├─ r.ok=false → markError(r.error)；缓存保持不动；return { ok:false, error }
 ├─ markSuccess({ lastSuccessAt: startedAt, cursor: startedAt, cursorBase:{ apiBaseUrl, serverStartedAt: health?.startedAt }, fullReason: win.fullReason, stats:{ uploaded, filtered, …r.data } })
 ├─ Promise.allSettled([refreshRanked(), refreshRecommendations(), refreshCleanup(), refreshRules(), getPrivacyConfig()])
 │                                          // 各模块导出的刷新函数，内部走 withCache 网络路径写缓存（PRD 6.8「SW 写入缓存」）
 └─ return { ok:true, data:{ syncState, result: r.data, fullReason: win.fullReason ?? null } }
```

- 刷新缓存只调用 RANK / REC / CLEAN / RULE 导出的 `refreshRanked` / `refreshRecommendations` / `refreshCleanup` / `refreshRules`（§11.1），SYNC 不自己构造这些接口的请求；推荐的请求体（currentPage 判定、隐私过滤、recentHistory）与缓存 key 由 REC 在 `refreshRecommendations` 内与 `GET_RECOMMENDATIONS` 共用同一实现，保证首页读到的就是同步后写入的那一份缓存。config 缓存由 `getPrivacyConfig()`（GET /api/config 成功即写 `cache.config`）刷新。单项刷新失败不影响同步结果（allSettled）。

- **防并发（F-SYNC-01 AC3）三道保险**：① `services/sync.js` 模块级 `inFlight` Promise 单飞，`SYNC_NOW`（用户点击 / 全量同步）与 `RECOVER_IF_NEEDED`（自动恢复）都只经 `runSync` 发 `POST /api/sync`；`chrome.storage` 读后写不是原子操作，所以**不再**用 `syncState.status==='syncing'` 判断是否放行；② popup 点击时在 `send` 之前**同步**把 `sync-button` / `sync-full-button` 置 `disabled`（经 bus `sync:requested` 让两个按钮一起置灰），响应返回或 `storage:syncState` 变为非 syncing 后恢复；③ storage 中的 `syncing` 状态驱动按钮置灰与状态行展示（重新打开 popup 时仍置灰）。
- 同步在 SW 中执行，popup 关闭不中断；`sendMessage` 未决期间 SW 保持存活，fetch 期间也不会被回收。
- `syncing` 超过 30 秒且本 SW 内 `isSyncInFlight()===false`（SW 被回收导致 `inFlight` 丢失、同步中断）时，`loadSyncState()` 把状态改为 `error`，`lastError = { code:'SYNC_INTERRUPTED', message:'同步中断（超过 30 秒未完成），请重试' }`（F-SYNC-06 AC5）。
- `activeTab` 同样遵循「系统页 / 无痕 / 敏感词命中 / url 为空 → 显式 `null`」，上行条目只含 `{ url, title[, lastAccessed] }`；`mode` 只取 `full | incremental`（契约不接受其他值），`cursor` 只在 incremental 时携带。
- 上传条数 `uploaded = (activeTab?1:0) + openTabs.length + history.length`（去重前），过滤条数 `filtered` 只计敏感词与无痕命中（系统页单独计 `skippedSystem`，不计入「过滤」）。

### 5.4 增量游标（C-FE-INCR-01）

| 场景 | mode | history.search startTime | 请求体 cursor |
|---|---|---|---|
| 首次同步（无 `syncState.cursor`）或点「全量同步」 | `full` | `now − 30 天` | 省略 |
| 之后的同步，且游标有效 | `incremental` | `cursor − 5 分钟` | `cursor` |
| 有游标但游标失效（见下） | `full` | `now − 30 天` | 省略 |

- `cursor` = 上次**成功**同步的开始时间（客户端时钟）；失败不推进。openTabs 每次全量上传（打开状态是快照，F-INCR-01 AC3）。
- **游标与后端实例绑定**：`syncState.cursorBase = { apiBaseUrl, serverStartedAt }`，成功同步时写入。同步前先 `GET /api/health`（3 s，复用诊断的结果结构），`isCursorValid` 满足任一条件即改为 `full`，并把原因写入 `syncState.fullReason`：
  1. `cursorBase.apiBaseUrl` ≠ 当前 `apiBaseUrl`（`api_base_changed`，如 F-DIAG-02 AC2 改到 4100 端口）；
  2. `health.persistence === 'memory'` 且 `health.startedAt > cursor`（`server_restarted`，后端内存模式重启）；
  3. `health.lastSyncAt === null` 或 `health.pageCount === 0`（`server_empty`，如测试中 `/api/__test__/reset`）。
  health 请求失败时不做判定（同步本身大概率也会失败，按原错误处理）。
- `SET_API_BASE_URL` 成功写入新地址后调用 `cursor.resetCursor()` 清空 `cursor` 与 `cursorBase`（双保险）。
- F-INCR-01 验收口径补充：同一后端、未重置的前提下第二次同步为 `incremental`（AC1）；后端被 reset / 内存模式重启 / 修改 API Base URL 后的下一次同步为 `full`，`fullReason` 非空，history 覆盖最近 30 天。诊断「最近一次同步」在这种情况下给出 warn「后端数据少于本地同步记录，请全量同步」（C-FE-DIAG-06）。

### 5.5 隐私过滤（C-FE-PRIV-01 ~ 03）

0. 冻结签名（与 §11.1 一致）：`getPrivacyConfig() → Promise<{ enabled, keywords, source }>`；`classifyUrl(url, keywords) → { uploadable, reason: 'system'|'sensitive'|'incognito'|null, keyword? }`；`filterForUpload(snapshot, privacy) → { payload, filteredCount, skippedSystem }`；`isUploadableTab(tab) → boolean`。调用方：SYNC、REC、MENU、CTX（`handlers/context.js` 生成 badge 与 `privacy{enabled,keywords,source}`）、DIAG（`checkPrivacy` 读 `enabled` / `source`）。`enabled=false` 时调用方以空关键词数组调用 `classifyUrl`（`filterForUpload` 内部同样处理），系统页 / 无痕仍判为不可上传。
1. 关键词来源（D-18）：`GET /api/config` 成功 → 使用 `privacySensitiveKeywords` 并写 `cache.config`；失败 → `cache.config`；再失败 → 内置 `['password','token','bank','secret']`。`enablePrivacyFilter=false` 时不做关键词过滤，但系统页 / 无痕仍然跳过。
2. 判定顺序：`incognito` → 非 http(s)（系统页）→ 完整 URL 转小写后包含任一关键词（`keyword.toLowerCase()`）。
3. 只在 background、**发送前**过滤；过滤结果只保留计数和本地标注（「含 password · 不上传」），不写 storage、不打日志（日志 URL 只留 host）。
4. 以下上行路径全部经过同一过滤，命中时**不发请求、不写 storage**：
   - 推荐请求的 `currentPage`（命中则显式传 `null`）/ `openTabs` / `recentHistory`；
   - 「添加到分析」（右键菜单与卡片按钮共用 `addToAnalysis`，`POST /api/pages/manual`）：本地命中直接提示「含敏感词未上传」；后端 `accepted:false` 同样提示；
   - `MARK_IMPORTANT`（☆ 与右键「标记为重要」）：本地命中不请求、不写 `importantUrls`，返回 `accepted:false`；后端返回 `accepted:false` 时回滚本地状态；当前页为敏感页时 ☆ 置灰并提示「敏感页面不采集」。
   - 推荐缓存 key 不使用原始 URL：非敏感页用 normalized URL（去 hash），被过滤 / 系统页统一为 `'__none__'`。
5. 已知局限：子串匹配会误伤 `tokenizer` 之类（D-18、FE-PRIV-03），文档说明，不打补丁。

### 5.6 缓存与离线（C-FE-CACHE-01 ~ 04）

- `withCache(name, fetcher, { source, key? })`：`source='cache'` 只读缓存（无缓存返回 `NO_CACHE`）；`source='network'`（默认）时后端成功 → 写 `cache[name] = { data, cachedAt: now }`，返回 `fromCache:false`；错误码为 `BACKEND_UNREACHABLE` / `TIMEOUT` 且有缓存 → 返回缓存 + `fromCache:true, offline:true, cachedAt`；无缓存 → 返回错误（视图显示 `*-error` 与「诊断」入口）。后端业务错误（4xx）不回退缓存。
- **排序缓存口径**（C-FE-RANK-01）：`cache.ranked` 是首页 Top 5 与离线展示的唯一来源，**只由无筛选（`openOnly` 为假、`domain` 为空）且 `limit = DEFAULTS.RANKED_LIMIT(50)` 的 `GET_RANKED` 与 `refreshRanked()` 写入**；带筛选或非默认 limit 的请求不经 `withCache`、不读不写缓存，直接 `callApi`，后端不可达 / 超时或 `source:'cache'` 时返回 `NO_CACHE`「筛选需要在线」，排序页签显示 `ranked-filter-offline-hint`，清空筛选即回到默认列表（可用缓存）。这样筛选结果不会污染首页 Top 5 与离线展示。
- 推荐缓存以 normalized 后的非敏感当前页 URL 为 key，被过滤 / 系统页统一为 `'__none__'`（最多保留 20 个 key）。
- 写操作（规则保存 / 删除 / 启停、整理执行、标记重要）成功后 `invalidate(['ranked','recommendations','cleanup'])`，视图随后走网络刷新。
- popup 首屏：`loadCacheFirst` 先发 `source:'cache'` 立即渲染，再发 `source:'network'` 刷新（stale-while-revalidate，F-CACHE-01 AC2）。
- 同一 ctx、消息及等价 payload 的在途首屏刷新共用一对 cache→network，并向后加入的视图重放缓存。视图用 `createRefreshQueue` 串行处理真实上下文变化和缓存失效：旧结果不再渲染，结束后保留一次后继刷新；推荐的隐式当前页不跨上下文复用旧请求。卸载后不再发送后续消息或渲染。
- `loadCacheFirst` 隔离消费者回调异常，并向迟加入者按序重放已交付阶段。`createSnapshotGate` 在首次缓存阶段暂存更新快照，cache 成功或 miss 后立即释放，保证缓存首帧先展示；后续以事件版本隔离迟到消息，不依赖 cachedAt 区分同毫秒的更新。筛选变化用刷新队列的 `replace()` 撤销旧请求，不把仍有效的默认缓存标记为失效。
- `storage:cache` 的完整快照直接更新视图，不再发送业务读取消息；忽略无关桶和仅时间变化。推荐只读当前有效 URL（去 hash）或 `__none__` 桶。整理经 `popup/lib/cleanup-cache.js` 只读本地快照与忽略表，和后台共用 `shared/cleanup-result.js` 的七天忽略过滤及汇总投影；原始响应缓存保持不变。隐藏整理页仅维护本地展示与 badge，进入页签后再成对刷新。
- 离线标识：api-client 在请求结果「在线 ↔ 离线」变化时写 `storage.connection`；`offline-banner.js` 在 `connection.status==='offline'` 且有缓存时显示「以下为 HH:mm 同步时缓存的结果」（HH:mm 取 `cache.cachedAt`）。
- 自动恢复（C-FE-CACHE-03）：恢复判断依赖粘性标记 `connection.recoverPending`，不看瞬时的 `connection.status`（popup 打开时 `CHECK_CONNECTION`、cache-first 的网络刷新、诊断页的重新检查都会把 status 写回 online，存在竞态）。
  1. 置位：api-client（C-FE-CORE-03）在请求结果为 `BACKEND_UNREACHABLE` / `TIMEOUT` 且之前 `recoverPending !== true` 时写 `{ status:'offline', recoverPending:true }`；之后的成功请求只把 `status` 改为 online，**不清除** `recoverPending`。
  2. 触发：popup 打开时 `offline-banner` 视图发送 `RECOVER_IF_NEEDED`；`maybeAutoResync()` 条件为 `connection.recoverPending===true` 或 `syncState.lastError.code ∈ {BACKEND_UNREACHABLE, TIMEOUT}`，且本次 `GET /api/health` 成功。
  3. 执行：`runSync({ trigger:'auto' })` **一次**——`runSync` 自身单飞（§5.3），若用户点击的同步正在进行则复用同一个 Promise、不另发 POST；recovery 另用模块级 in-flight Promise 合并并发的 `RECOVER_IF_NEEDED`（health 探测只做一次）；成功后由 recovery 写 `recoverPending:false`（唯一清除点），connection 为 online，提示条消失（F-CACHE-02 AC2）；失败时保留标记，下次打开 popup 再试。
  4. 返回 `{ resynced: boolean, reason: 'not-needed'|'backend-down'|'synced'|'sync-failed'|'in-flight' }`。

### 5.8 右键菜单（C-FE-MENU-01 ~ 03）

- `runtime.onInstalled` 中 `contextMenus.removeAll()` 后创建 `nav-add`「添加到分析」、`nav-important`「标记为重要」，`documentUrlPatterns: ['http://*/*','https://*/*']`。

- **同一路径的界面入口**：当前页面卡片上除 ☆ 外还有「添加到分析」按钮（testId `current-page-add`，系统页不显示，C-FE-MENU-03 渲染），点击发送 `ADD_TO_ANALYSIS { url, title }`，由 `handlers/important.js` 的 `handlers.ADD_TO_ANALYSIS` 直接调用 `context-menu.js` 导出的 `addToAnalysis(url, title)`——与右键菜单完全相同的函数，不是测试专用入口，也不检测测试环境（FE-TEST-01）。

所有 key 定义在 `shared/storage-keys.js`（FE-CACHE-01），与 `ui-contract.storageKeys` 一致：

## 7 接口依赖与对齐结论

成功判定统一为 **2xx（`res.ok`）**，`POST /api/rules` 为 201；非 2xx 解析 `{ error: { code, message, details } }` 并原样透传 code；非 JSON 映射为 `INVALID_RESPONSE`（C-FE-CORE-03）。

| 接口 | 使用方 | 超时 / 重试 | 依赖的响应字段 |
|---|---|---|---|

| 后端响应 | 消息 | 映射 |
|---|---|---|
| `DELETE /api/rules/:id` → `{ deleted, ruleCount }` | `DELETE_RULE` | `{ id: deleted, deleted: true, ruleCount }`，并按 ruleCount 刷新 `cache.rules` |
| `PATCH /api/rules/:id` → 规则对象 | `TOGGLE_RULE` | `{ rule: body }` |

| `POST /api/pages/archive` → `{ ok, affected, archivedAt, notFound }` | `CLEANUP_ARCHIVE` | `{ archived: affected, notFound, undoToken }` |
| `POST /api/pages/unarchive` → `{ ok, affected, notFound }` | `CLEANUP_UNARCHIVE` | `{ unarchived: affected, notFound }` |
| `POST /api/pages/merge` → `{ ok, keepUrl, merged }` | `CLEANUP_MERGE` | `{ archived: merged, keepUrl, undoToken:{ kind:'merge', urls: urls − keepUrl } }` |
| archive / unarchive / merge 返回 404 | 上述三者 | `ok:false, NOT_FOUND`「建议已失效，已刷新列表」，cleanup 缓存失效，视图重新拉取 |
| `POST /api/pages/important` → `{ accepted, … }` | `MARK_IMPORTANT` | `accepted:false` → 回滚，返回 `{ accepted:false, reason:'sensitive' }` |
| `GET /api/pages/ranked` → `{ pages, total, domains }` | `GET_RANKED` | 原样 + 缓存标记 |
| `GET /api/pages/cleanup-suggestions` | `GET_CLEANUP` | 按后端 `key` 剔除已忽略项后重算 summary，加 `pendingCount` |

已与 api-contract 确认的结论：

1. 默认端口 3000（`defaultPort`），插件默认 `http://127.0.0.1:3000`（FE-API-02：`http://127.0.0.1:<defaultPort>`；与后端默认 HOST=127.0.0.1 一致，避免 `localhost` 先解析为 `::1` 导致连不上）。
2. 错误统一 `{ error: { code, message, details? } }`（D-16）。
3. `GET /api/pages/ranked` 支持 `limit`、`openOnly=true`、`domain`，并返回不受过滤影响的 `domains`；插件取 `limit=50`，首页只渲染前 5。筛选**只走后端**，插件端不做二次过滤。
4. `POST /api/pages/archive|unarchive` 请求体 `{ urls: string[] }`，`merge` 为 `{ urls, keepUrl }`，`important` 为 `{ url, title, important }`。
5. 「添加到分析」使用独立接口 `POST /api/pages/manual { url, title }`（sources 含 manual，不影响 isOpen 快照）。
6. `POST /api/recommendations/next` 的 `currentPage`、`POST /api/sync` 的 `activeTab` 为必带 key，可为 `null`。
7. 整理建议使用后端返回的稳定 `key`（archive / keep 为 normalizedUrl 相关，merge 为 `merge:<dupKey>`），前端不自造。
8. CORS 允许 `chrome-extension://*` 来源（host_permissions 已授权时 SW 的 fetch 不受 CORS 限制）。

## 11 文件所有权表

由 `node .workflow/validators/validate.mjs pack` 生成 `.workflow/context/packs/ownership.json`。同一文件只属于一个业务模块；多个模块共用的文件登记为 CORE，由 lead 维护。lead 在模块开发开始前先落地全部 CORE 文件，并在 `handlers/index.js` / `views/index.js` 中注册所有模块文件。模块文件不是空占位，而是**导出桩**：lead 按 `ownership.json` 为每个业务模块文件生成桩文件，把 §12 / code-points-fe.json 中登记的全部 symbols 都具名导出，附 JSDoc 签名（参数、返回结构取自 §12.1），函数体抛 `{ code:'NOT_IMPLEMENTED', message:'<symbol> 尚未实现' }`（`handlers` 对象按登记的 type 逐个放入同样会抛错的函数，`mount()` 渲染空容器），桩文件不写 `@code` 标注（由模块开发者实现时补）。原因：SW 为 `type: module`，ESM 导入不存在的具名导出会在链接阶段报 SyntaxError，整个 Service Worker 起不来，所有模块组的 UI 测试会一起失败；导出桩保证任一模块未完成时其他模块仍可加载与测试（调用到未完成模块时只得到 `NOT_IMPLEMENTED` 错误），模块开发者只改自己名下的文件，需要改 CORE 文件时写进 `blockedBy`。
