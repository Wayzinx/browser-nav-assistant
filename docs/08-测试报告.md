  - `extension/background/handlers/cleanup-actions.js`（C-FE-CLEAN-02，F-CLEAN-08）2.5%。该文件被 TC-UI-CLEAN-003～TC-UI-CLEAN-009、TC-UI-CLEAN-011、TC-UI-CLEAN-012 引用，这些用例都通过，并且断言了归档 / 合并 / 撤销后后端数据的真实变化，说明代码确实执行过。行覆盖率偏低更可能是 service worker 中这部分执行的覆盖率没有被导出（例如 SW 被重启后 `__coverage__` 丢失），属于采集口径问题，建议 QA 排查夹具的 SW 覆盖率导出时机。

- 变异检查：杀死率 85.9%（1136/1323），达到 T4 阈值 ≥ 80%；没有 `mutation-ignore` 豁免项。存活算子分布：

## 10. 风险与建议

1. 覆盖率采集口径存在盲区：独立 spawn 的后端子进程（PERSIST）和部分 service worker 执行（cleanup-actions.js）没有计入 → 覆盖率数字低估了实际执行范围，可能掩盖真正的未覆盖代码 → QA 在 PERSIST 用例中保留 `NODE_V8_COVERAGE` 并单独汇总，排查 SW 覆盖率导出时机。
2. TC-API-SYNC-001 写死了后端日志路径 → 在覆盖率运行和变异运行中都基线失败，降低这两类数据的可信度 → QA 改为读取 `SERVER_LOG_FILE` / `LOG_FILE` 环境变量（与 playwright.config.mjs 一致）。
3. 排序类接口的顺序断言不足：`reverse` 变异大量存活 → 若排序逻辑回归，部分用例发现不了 → QA 为 ranked、推荐等顺序有语义的接口补顺序断言，其余列表显式豁免。
4. 少数用例未断言状态码（TC-API-RANK-016、TC-API-RANK-017、TC-API-RANK-018、TC-API-RANK-020）→ 错误响应可能被漏判 → QA 补状态码断言。
5. 变异运行中 4 个用例基线未通过（第 6 节）→ 变异数据对这 4 个用例不完整 → QA 单独复跑变异检查。
6. ACCEPTANCE-BUG-1 的修复没有自动化断言覆盖悬停态 → 可能回归 → 演示前人工复看，后续可加入 UI 用例的悬停截图核对。
